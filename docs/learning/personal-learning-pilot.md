# A small personal learning pilot

Use this guide to find out whether the improved workflow makes independent
practice easier to complete and more useful. It is a plan, not a record of
learning already performed or evidence that Terrain improves learning outcomes.
Keep the complete roadmap, current deep-study topic and one active project
milestone. Use existing Skill checks; do not introduce another progress tracker.

## Before the first check

- Confirm that the same practice-repository commit can be obtained and checked on
  both computers, and that a saved Terrain note can be resumed on the other one.
  Fix reproducibility problems before attributing failures to subject knowledge.
- Choose a few small objectives within the current learned branch, expressed as
  actions: explain an execution trace, diagnose a fault or adapt a design to one
  changed constraint. Do not add future chapters or solve a pending assessment.
- Prepare concrete changed cases and observable criteria. Review the rubric and,
  for code, validate a separate reference implementation with meaningful tests.
  Do not expose the solution or supplied reasoning steps in ordinary lesson
  exports, notes or the practice README. If the learner has already seen a case's
  solution, replace that case before treating it as an independent check.
- State the permitted tools before the attempt. `documentation` permits the
  agreed documentation; `closed_book` measures recall without sources. AI hints,
  generated core code and a supplied solution are help, even if the tests pass.
- Choose a later day and a 20–30 minute slot inside the existing weekly budget.
  About seven days is a practical starting point, not an optimal interval for
  every skill. Keep only as many pending checks as that budget can support.

Do not create artificial baseline results. Recent observed attempts may inform
the starting level; otherwise record it as unknown. When calibration is needed,
use one to three relevant open attempts in total, without repeatedly testing
already demonstrated foundations. Keep uncertainty and help visible.

## Use the existing app records

1. After substantial practice, open **Skill checks** for the actual topic or
   project milestone. The contextual shortcut after session import leads to the
   same planning workflow; opening it records no learning result.
2. Optionally paste one separate `terrain-practice` block from the tutor into
   **Use a tutor's practice suggestion**. It supplies only the kind, task,
   success criteria and allowed tools. Choose the target and dates yourself,
   review the draft and explicitly schedule it. Keep it separate from the
   `learning-os` or `terrain-project` import.
3. On the due day, attempt the changed case before feedback. Record the original
   reasoning, observed outputs, permitted documentation and any other help.
   Link the exact repository commit and file/test command where relevant. A URL
   or a green test alone is not evidence that the learner did the work unaided.
4. Save the first attempt before requesting feedback. Evaluate it against the
   agreed criteria. A corrected answer remains supported practice; do not replace
   the first attempt, award a second recall grade or report it as a fresh unaided
   success. A further independent attempt needs a new changed case on a later day.
5. Record `passed` or `needs_practice` only when the evidence supports the result,
   with the actual reviewer: `self`, `ai` or `human`. A self-assessment is useful
   but is not an independent human review. Ask another engineer to review a
   selected artifact when useful; record that review only after it happens.
6. If the task, reference or rubric is faulty or ambiguous, leave the result
   unresolved while clarifying it. Do not count the tutor's mistake as the
   learner's failure. Record one specific next action instead of a broad label
   such as “weak at Solidity.” A pass applies to this task and its tool policy,
   not to every objective in the topic.

The existing plan stores the target, dates, task, criteria and allowed tools;
the attempt stores first reasoning, evidence and assistance; the result stores
feedback, next action and reviewer. Use those records for actual learning evidence.
Administrative pilot notes need only the following fields, recorded when known:

| Pilot field | What to record |
|---|---|
| Task version | Stable local label and date for the exact task/rubric used |
| Starting evidence | Observed prior attempt, or unknown; do not manufacture a score |
| Planning route | Manual topic/milestone navigation or contextual import shortcut |
| Time and completion | Actual planning/attempt time, completion or reason for postponement |
| Device handoff | Whether the saved note and exact commit resumed successfully |
| Assessment issue | Missing evidence, ambiguous rubric or solution leakage, if observed |

Keep these administrative notes in a small private pilot log, separate from topic
notes about material actually studied. Do not copy entire conversations or
duplicate the Skill check's result there. No example row here represents a learner
record.

## Compare and decide

For a simple comparison, choose the planning route in advance for different,
reasonably comparable objectives: manual navigation for some and the contextual
shortcut for others. Keep learning materials, tool policy and time budget similar.
Do not repeat the same learned task as an “unlearned” control; practice carries
over, and task difficulty will still limit comparison.

For learning, inspect completion of changed tasks after a delay with the agreed
tools. For the shortcut, inspect whether planning and actually attempting a check
became easier. Also consider assistance, recurring errors, uncertainty, time,
postponements and device handoff. Messages sent, streaks and topics activated do
not substitute for those outcomes. Choose practical success criteria before the
pilot, based on observed baseline friction; do not invent a percentage gain.

Pause the affected assessment if an answer leaks, the original attempt is lost,
or a result claims independence despite disallowed help. Clarify an ambiguous
rubric before assigning a result. If checks repeatedly exceed the budget or the
shortcut adds friction without useful attempts, reduce the queue or use the
manual route. Expand only when the evidence is useful and the workload remains
sustainable.

Review this once a week within the [existing weekly allocation](study-workflow.md).
For one learner, the outcome is evidence about usability and personal usefulness,
not a statistically established causal effect of an AI tutor or Terrain.
