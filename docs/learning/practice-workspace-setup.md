# Настройка локального Web3 workspace

Пакет из 16 файлов применён 14 октября 2026 к существующему
`/Users/dmitrijgorbatenko/personal/web3-practice`; затем явно закреплена EVM в двух
compiler-конфигурациях. Полная локальная проверка прошла. Публикация на GitHub и
синхронизация с другим компьютером ещё не выполнялись. Все учебные компьютеры
пользователя работают на macOS.

## Что меняется

- Сохраняются текущие упражнения, незавершённые решения, изменения зависимостей
  и их пути. Ни одна будущая учебная задача не решается автоматически.
- Применяются проверенные изменения из прежнего плана hygiene: публичная
  демонстрационная фикстура, отсутствие логирования исходного private key и
  объекта аккаунта, сравнение вычисленного адреса с viem. Исходное значение не
  печатается и не включается в пакет.
- `yarn test` включает карту артефактов, три существующие TS-проверки и Foundry.
  `yarn check` добавляет проверку типов и Hardhat build. Для TS используется
  встроенная поддержка Node; единственная правка Merkle-теста меняет расширение
  относительного импорта `.js` → `.ts`, не его проверки или алгоритм.
- Node 24.2.0, Yarn 4.17.0, Foundry 1.7.1 и Solidity 0.8.35 фиксируются как
  исследованный baseline. Это не утверждение об актуальности последних релизов.
  При обновлении инструментария следует менять обе локальные установки и CI
  вместе, затем запускать тот же набор проверок.
- В Foundry и Hardhat явно закреплены EVM `osaka` и optimizer `true / 200`.
  Это baseline существующего окружения. Для эксперимента о другом форке нужно
  явно выбрать соответствующую версию в обоих инструментах и записать её в evidence.
  Совпадение этих параметров не обещает идентичность всех metadata/bytecode.
- Добавляются CI, карта «тема → существующий файл → команда», инструкции для
  нескольких локальных компьютеров. Планируемые пути подписаны `planned`.
  Данные прогресса, оценки и полные личные конспекты в Git не дублируются.

Используется существующий `yarn.lock`, новые зависимости не устанавливаются.
Обновление не добавляет remote, не выполняет Git commit/push, не создаёт проекты
на GitHub и не импортирует результаты обучения в Terrain.

## Применение

На основном Mac пакет уже применён. Следующие команды сохранены для проверки
пакета и воспроизведения процедуры; на втором Mac следует клонировать готовый
учебный репозиторий, а не повторно применять миграцию. Последующие изменения
документации вносятся отдельно: установленная квитанция защищает поздние правки.

Из корня Terrain сначала просмотреть список файлов:

```sh
python3 scripts/practice-workspace/setup.py /Users/dmitrijgorbatenko/personal/web3-practice
```

Применить тот же пакет при наличии разрешения на запись в отдельный репозиторий:

```sh
python3 scripts/practice-workspace/setup.py /Users/dmitrijgorbatenko/personal/web3-practice --apply
```

Перед первой записью скрипт сверяет SHA-256 всех затрагиваемых исходных файлов
с изученной версией, проверяет отсутствие новых целевых файлов и запрещает
symlink/выход за каталог. При отличии останавливается без записи. Нельзя обходить
защиту или подменять хеши: нужно заново изучить изменения и подготовить пакет.
Запись каждого файла атомарна; при обнаруженной ошибке уже записанные файлы
восстанавливаются. На время применения закройте редактирование этих файлов;
это не распределённая файловая транзакция и не защита от аварийного отключения.

`.terrain-workspace-setup.json` хранит только версию пакета и хеши установленных
файлов. Повторный запуск ничего не перезаписывает и перечисляет более поздние
правки, если они есть. Это квитанция установки, не журнал учебного прогресса.

Прежний `apply-practice-hygiene.py` после этого пакета запускать не нужно:
его изменения включены, а исходные хеши закономерно перестанут совпадать.

## Проверка

```sh
python3 -m unittest discover -s scripts/practice-workspace -p 'test_*.py'
yarn --cwd /Users/dmitrijgorbatenko/personal/web3-practice check
```

Временная копия нужна только для проверки пакета; настоящий репозиторий должен
пройти проверки после применения. Первая установка зависимостей и загрузка
компиляторов могут потребовать сеть. Проверка на GitHub станет возможна после
настройки remote и явной публикации; локальный проход не выдаётся за запуск CI.

14 октября полный `yarn check` прошёл в настоящем `web3-practice`: типы,
карта из пяти записей, три TS-проверки, один Foundry scaffold и Hardhat build.
После явной фиксации EVM Hardhat сообщил компиляцию одного Solidity-файла с
solc 0.8.35 / osaka. Первоначальное ограничение доступа к compiler cache снято
для проверки; запуск CI на GitHub и проверка второго Mac ещё не выполнялись.

На этом Mac одновременно установлены Homebrew Node 24.2.0 и NVM Node 24.10.0.
Если обычный `yarn check` сообщает несовпадение версии, сначала выбрать 24.2.0
менеджером версий. Проверенный запуск установленного Homebrew baseline из
каталога `web3-practice`:

```sh
/opt/homebrew/Cellar/node/24.2.0/bin/node \
  /opt/homebrew/Cellar/node/24.2.0/lib/node_modules/corepack/dist/yarn.js check
```

Этот абсолютный путь относится только к проверенному Mac; на остальных
использовать собственную установку той же версии, а не копировать путь буквально.

Перед первым commit/push просмотреть выбранные изменённые файлы и локальные
значения по существующему [hygiene-плану](practice-hygiene.md). Не добавлять
невыбранные личные файлы командой, автоматически захватывающей весь каталог.

Три существующие TS-проверки и Foundry scaffold проверяют ограниченные случаи;
они не доказывают завершённость всех лабораторных. Это прямо указано в карте,
README и workflow. Цель — воспроизводимость и продолжение глубокой учёбы.

## Ежедневная работа

Один приватный remote, отдельный clone на каждом компьютере, одинаковые версии.
Начало: проверить branch/локальные изменения, получить изменения через
`git pull --ff-only`, открыть тему и следующий шаг в Terrain. Остановка:
проверить выбранный артефакт, сохранить небольшой checkpoint commit, отправить
push, записать ссылку на commit и следующий шаг в Terrain. Незавершённую работу
можно сохранять в ветке темы; незакоммиченные/неотправленные файлы на другой
компьютер не попадут. При офлайн-работе продолжать на том же устройстве до push.

## Подключение второго Mac

Пользователь подтвердил фиксацию изменений локальными коммитами. Remote не
подключён, код не отправлен: рабочие копии ещё не синхронизируются.
Инструкция ниже описывает следующий этап после публикации. Дополнительное
уточнение под macOS подготовлено в этой инструкции и шаблоне
`scripts/practice-workspace/templates/docs/local-workflow.md`; копирование этого
уточнения в существующий `web3-practice/docs/local-workflow.md` не выполнялось,
так как запрос записи был отклонён. Базовый workflow в учебном repo уже есть.

После публикации приватного репозитория клонировать его фактический URL с
`git clone --recurse-submodules`. На каждом Mac отдельно установить одинаковые
версии Node и Foundry из `.node-version` и `.foundry-version`. Для Apple Silicon
использовать нативные arm64-сборки и обычный Terminal без Rosetta; для Intel —
x64/x86_64. `uname -m` показывает архитектуру shell, `node -p process.arch` —
архитектуру установленного Node. Сами исходники и файлы версий общие.

Использовать уже выбранный менеджер версий Node. Например, при установленном nvm:

```sh
nvm install "$(cat .node-version)"
nvm use "$(cat .node-version)"
foundryup --install "$(cat .foundry-version)"
corepack enable
git submodule update --init --recursive
yarn install --immutable
yarn check
```

Команда `foundryup` предполагает, что установщик Foundry уже установлен на этом
Mac. Не копировать `node_modules`, compiler cache и сборочные каталоги между
машинами: локальная установка создаёт зависимости под нужный процессор.
Рабочий каталог не помещать в iCloud Drive для параллельной синхронизации файлов;
передача исходников идёт через выбранный Git remote. Существующие lockfile и
ревизия submodule сохраняются. После установки каждый Mac отдельно должен пройти
`yarn check`; локальный проход на первом Mac не проверяет второй.

Сохраняется весь пошаговый курс Web3. Wallet → indexer → escrow — дополнительная
практическая ветка по готовности, не замена основного изучения. Качественный
артефакт содержит проверяемую реализацию, отказной случай, объяснение решения
и самостоятельную защиту при изменении условия. Это поддерживает будущий
переход на более сильную роль, но не задаёт гарантию зарплаты или срока.
